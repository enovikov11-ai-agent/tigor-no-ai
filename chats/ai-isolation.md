I’ll organize this as a defense-in-depth model: identity/tenant boundaries, filesystem/process isolation, network/data-flow control, build provenance, runtime policy, and AI-agent-specific guardrails. I’ll also call out which controls are actually security boundaries versus just useful hygiene.

---------------------

For **semi-trusted code maintained/generated by an AI agent**, I would assume three independent failure modes:

1. the code itself becomes malicious,
2. the agent is prompt-injected / confused and makes an unsafe change,
3. the surrounding toolchain, dependency, or runtime gets compromised.

So the architecture should make **the code, the agent, and the build/runtime mutually distrustful**. Containers + ACLs alone are not enough.

A useful mental model is:

> **Agent → source tree → builder → artifact → deployment → runtime**
>
> Every arrow is a trust boundary.
> Every stage should receive capabilities, not ambient authority.

## 1. Strong tenant boundary

I'd make the fundamental isolation unit something like:

`tenant / user / project / execution`

rather than merely one Unix account per user.

For every execution/job:

- unique workload identity
- unique PID namespace
- unique mount namespace
- unique network namespace
- unique IPC namespace
- separate cgroup
- ideally unique VM/microVM for hostile workloads
- ephemeral filesystem
- ephemeral credentials
- explicit input/output channels

Do **not** trust tenant IDs coming from the program:

```text
BAD:
request.tenant_id -> /storage/$tenant_id

GOOD:
authenticated principal
↓
control plane derives tenant
↓
capability / scoped mount / scoped token
```

In other words, tenant isolation should happen **before the untrusted process gets control**.

For storage, consider:

```text
tenant
├── source RO
├── workspace RW
├── cache RW (tenant-specific)
├── dependencies RO
└── output write-only
```

Avoid shared writable caches. They're a surprisingly good cross-tenant attack channel.

For high-value tenants, separate:

- object-store namespace
- database credentials
- KMS key
- encryption context
- registry namespace
- build cache

A compromised tenant then cannot merely guess another tenant's path.

---

# 2. Capability model rather than ACL model

Traditional ACL:

> Process X can access `/foo/bar`.

Capability model:

> Process X is handed **exactly one already-authorized handle** to the thing it needs.

The latter is much easier to reason about for AI-generated software.

Examples:

- pre-opened FD instead of filesystem tree
- Unix socket instead of network access
- opaque object capability instead of cloud API credentials
- broker API instead of AWS/GCP/Azure token
- signed upload URL instead of storage credentials
- per-request database proxy instead of DB password
- narrowly scoped RPC method instead of service identity

An AI-managed process should ideally have **almost zero ambient authority**.

---

# 3. Separate control plane from execution plane

This is probably one of the most important architectural properties.

The AI agent should not itself possess:

- hypervisor control
- production credentials
- policy configuration access
- signing keys
- CI root credentials
- tenant database credentials
- ability to modify its sandbox policy

Instead:

```text
Trusted control plane
/ | \
/ | \
policy credential artifact
engine broker broker
| | |
+------ execution --------+
plane
|
untrusted code
```

The agent **requests actions**.

A trusted service decides whether they're allowed.

For example:

```text
agent:
"give this process github access"

broker:
"no"

agent:
"read repository foo at commit abc123"

broker:
"allowed: here is a read-only snapshot"
```

This massively reduces the consequences of prompt injection.

# 4. Runtime isolation hierarchy

I'd roughly rank common approaches like this:

| Mechanism | Good for | Security boundary |
|---|---|---|
| language sandbox | cooperative code | weak |
| Docker/container | trusted-ish services | moderate/weak against kernel attacks |
| namespaces + seccomp + LSM | hardened containers | moderate |
| gVisor | semi/untrusted code | strong |
| Kata | untrusted multi-tenancy | strong |
| microVM/KVM | hostile workloads | very strong |
| separate physical host | exceptional workloads | strongest practical |

gVisor explicitly treats host-kernel exposure as an important weakness of ordinary Linux isolation and inserts its own application kernel between workload and host. citeturn812510search8

Firecracker assumes guest vCPU execution may be malicious and layers KVM, seccomp, namespaces, cgroups and privilege dropping around it; importantly, Firecracker itself explicitly says **egress filtering must be implemented outside the VM**. citeturn812510search6

Kata similarly emphasizes that VM isolation by itself does **not** magically produce multi-tenancy—you still need storage, network and control-plane isolation. citeturn812510search15

For AI-maintained arbitrary native code, I'd lean toward:

```text
microVM
+
minimal guest kernel
+
RO image
+
tmpfs workspace
+
external network proxy
+
external credential broker
```

rather than betting everything on seccomp.

# 5. Linux inner sandbox

Even inside a VM, reduce blast radius.

Use:

- non-root UID
- no supplementary groups
- no Linux capabilities
- `no_new_privs`
- seccomp allowlist
- Landlock
- AppArmor/SELinux
- PID namespace
- mount namespace
- network namespace
- user namespace where appropriate
- cgroups v2
- readonly root FS
- tmpfs `/tmp`
- `nodev`
- `nosuid`
- `noexec` where workable
- no writable `/proc/sys`
- no host `/sys`
- no raw block devices
- no `/dev/kvm`
- no `/dev/mem`
- no Docker/containerd socket
- no host PID namespace
- no host IPC namespace

Landlock is particularly interesting here because an **unprivileged process can further restrict itself**, and Landlock restrictions stack with existing DAC/LSM controls rather than replacing them. Current kernel documentation explicitly positions it as a sandboxing layer for compromised or malicious userspace. citeturn812510search1turn812510search4

Also block or carefully consider:

- `ptrace`
- `perf_event_open`
- `bpf`
- `io_uring`
- unusual `ioctl`s
- keyrings
- namespace creation
- mounting
- FUSE
- raw sockets
- packet sockets

Generic seccomp profiles tend to become permissive over time. Treat them as **attack-surface reduction**, not your primary tenant boundary.

# 6. Resource isolation is security

AI-generated software can accidentally implement:

```c
while (1) fork();
```

or deliberately:

- allocate all RAM
- fill disk
- exhaust inodes
- create millions of sockets
- consume connection tracking
- consume entropy
- saturate CPU
- hammer DNS
- produce 1 TB logs

So put quotas on:

- CPU
- memory
- swap
- disk bytes
- inodes
- processes/PIDs
- open FDs
- sockets
- network bandwidth
- network connections/sec
- DNS requests
- API requests
- log volume
- runtime duration

Also limit output artifact size.

Otherwise your "security boundary" becomes a DoS API.

# 7. Network should be deny-by-default

I strongly agree with your **proxy/diode** idea.

Ideally the workload has:

```text
NO direct Internet route
NO LAN route
NO RFC1918 route
NO metadata route
NO IPv6 surprise route
```

Instead:

```text
workload
|
v
egress proxy
|
policy engine
|
Internet
```

Block:

- `127.0.0.0/8` except intentional loopback
- RFC1918
- link-local
- cloud metadata addresses
- Kubernetes API
- service network
- host bridge address
- hypervisor management network
- internal DNS
- multicast/broadcast

Be careful about **IPv6 bypasses**.

## Proxy policies

Give each sandbox a unique proxy identity.

Then log:

```text
workload
tenant
destination
IP
port
SNI
HTTP host
HTTP method
bytes in/out
DNS resolution
policy decision
```

You can enforce:

```text
github.com:443 ALLOW
pypi.org:443 ALLOW
files.pythonhosted.org ALLOW
*.internal DENY
everything else DENY
```

For builds, the better model is often:

> no Internet at all.

Dependencies come from a controlled mirror.

# 8. Data diode pattern

This is extremely powerful.

Instead of giving a workload arbitrary filesystem/network connectivity:

```text
INPUT STORE
|
v
sandbox
|
v
OUTPUT STORE
```

with no reverse path.

For example:

### Input

Signed immutable bundle:

```text
source.tar
dependencies.tar
task.json
```

### Output

Only:

```text
artifact
stdout
stderr
test report
SBOM
```

The sandbox cannot modify the input repository or infrastructure.

A trusted controller later decides whether the output can progress.

This turns a complex access-control problem into a much simpler **information-flow problem**.

# 9. Separate build from runtime

Don't let code that compiled itself deploy itself.

Use:

```text
AI
↓
Git commit
↓
isolated builder
↓
artifact
↓
verification
↓
signing
↓
artifact registry
↓
deployment controller
```

Never:

```text
AI → ssh production
```

and preferably not:

```text
CI job → kubectl production
```

Production deployment should be triggered by an independently authenticated control plane.

# 10. Hermetic / reproducible builds

Yes—this belongs near the center of the architecture.

Aim for:

- pinned compiler
- pinned base image
- pinned dependencies
- lockfiles
- content hashes
- no network during compilation
- deterministic timestamps
- deterministic environment
- immutable build image
- source commit hash captured
- dependency hashes captured

Then do **independent rebuilds** occasionally:

```text
builder A → SHA256 X
builder B → SHA256 X
```

If:

```text
X != Y
```

something requires investigation.

Reproducibility isn't sufficient by itself—perfectly reproducible malware exists—but it greatly improves provenance.

# 11. Build provenance

I'd implement SLSA-style provenance.

Record:

```text
source commit
builder identity
build image
build command
inputs
dependencies
environment
outputs + digests
timestamp
```

Critically, **the build workload must not be able to forge its own provenance**.

SLSA's higher assurance requirements explicitly call for provenance to be generated/verified by the trusted build service, with signing material inaccessible to user-controlled build steps. citeturn812510search2turn812510search7

That distinction matters enormously for AI builds.

# 12. Artifact signing and promotion

Separate:

```text
BUILD
TEST
SIGN
PROMOTE
DEPLOY
```

Different identities.

An AI build job should not have signing credentials.

Use something like:

```text
artifact digest
+
build provenance
+
SBOM
+
test attestation
+
policy decision
↓
signer
```

Sigstore/Cosign's identity-based signing can bind artifact signatures to OIDC identities while recording signing events in a transparency log. citeturn812510search0

For internally controlled infrastructure, HSM/KMS-backed signing can also make sense.

# 13. Supply-chain ACLs

AI agents are particularly likely to "helpfully" add dependencies.

I'd therefore have a package firewall.

Instead of:

```text
pip install whatever-agent-invented
```

use:

```text
PyPI
↓
quarantine mirror
↓
package policy
↓
approved mirror
↓
builder
```

Policies can check:

- exact package
- exact version
- hash
- age
- maintainer
- provenance
- signature
- known vulnerabilities
- license

- postinstall hooks

- transitive dependency count

Especially scrutinize:

- npm lifecycle scripts
- Cargo `build.rs`

# 14. Immutable tests the agent cannot edit

This is one people often miss.

If the agent can modify:

```text
implementation
+
tests
+
CI
```

then:

> "all tests pass"

means almost nothing.

Maintain some **external tests** that the AI cannot modify.

Example:

```text
repo/
tests/ AI writable

verification-system/
reference-tests/ AI cannot read/write
```

You can have:

- hidden regression tests
- invariant/property tests
- fuzzers
- compatibility corpus
- golden output tests
- security tests

This creates an independent oracle.

# 15. The agent must not control policy

Put security policy elsewhere.

Agent cannot edit:

```text
sandbox profile
network ACL
CI trust rules
branch protections
approval policy
signing configuration
deployment policy
reference tests
secret broker
```

Ideally those aren't even in the same repository.

Otherwise the AI eventually discovers:

```yaml
security:
allowEverything: true
```

is a convenient way to solve its task.

# 16. Two-person / two-agent principle

For higher-risk changes:

```text
generator
↓
patch
↓
independent reviewer
↓
policy verifier
```

Reviewer should **not inherit the generator's conversation/context**, because otherwise prompt injection can propagate.

You can even use heterogeneous systems:

```text
Agent A writes code
Agent B reviews
deterministic tooling verifies
human approves high-risk categories
```

Independence matters more than having ten identical reviewers.

Automatically elevate changes involving:

- authentication
- authorization
- crypto
- secret handling
- deserialization
- parsers
- shell execution
- SQL
- network policy
- filesystem permissions
- container configuration
- CI
- dependency changes
- package lockfiles

# 18. Secretless workloads

The ideal untrusted workload has:

> **zero secrets.**

When access is needed:

```text
sandbox
↓
credential broker
↓
short-lived capability
```

Prefer:

- OIDC workload identity
- mTLS workload certs
- short-lived JWTs
- scoped SAS/presigned URLs
- temporary DB credentials

over:

```text
AWS_SECRET_ACCESS_KEY=...
```

Make credentials:

- single-purpose
- tenant-scoped
- short-lived
- audience-bound
- non-renewable by workload

Best is often to **not reveal credentials at all**:

```text
sandbox → broker → service
```

The broker performs the privileged request.

# 19. Secret exfiltration controls

One subtle issue:

If a process has **both**:

```text
read(secret)
+
network(anywhere)
```

your security model is already mostly over.

Capability composition matters.

A strong pattern is:

| Workload | Secrets | Internet |
|---|---:|---:|
| dependency fetcher | no | restricted |
| compiler | no | no |
| test runner | synthetic only | no |
| deploy controller | yes | no arbitrary egress |
| runtime | limited | allowlisted |

Don't put powerful capabilities together unless necessary.

# 20. Browser isolation

For your CSP point: yes, but I'd go farther.

If AI-generated content/code is exposed to users in a browser, give it a **separate origin**.

Prefer:

```text
trusted:
app.example.com

untrusted:
random-id.example-sandbox.net
```

over:

```text
app.example.com/user-content/foo
```

And preferably even avoid sharing the same registrable domain.

Why?

Because of:

- cookies
- `Domain=` cookies
- service workers
- same-site behavior
- authentication assumptions
- legacy browser behavior
- origin confusion

## Browser controls

For untrusted output consider:

```http
Content-Security-Policy:
default-src 'none';
script-src 'none';
connect-src 'none';
img-src 'self' data:;
style-src 'self';
frame-ancestors 'none';
base-uri 'none';
form-action 'none';

X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=()
```

Adjust for your application.

Also consider:

- CSP nonces/hashes
- Trusted Types
- COOP
- COEP
- CORP
- strict CORS
- Fetch Metadata headers
- iframe sandbox
- disable forms
- disable top navigation
- disable popups
- disable downloads
- disable worker creation
- strict MIME types

# 21. CSP supplied separately from content

Your idea of **serving CSP independently from the generated code/content** is excellent.

Don't let generated HTML say:

```html
<meta http-equiv="Content-Security-Policy"
content="default-src * 'unsafe-inline'">
```

and treat that as authoritative.

Instead:

```text
trusted reverse proxy
↓
adds security headers
↓
untrusted response
```

The AI cannot modify the reverse proxy.

Same principle applies to:

- CORS
- cookies
- COOP
- COEP
- cache headers
- download disposition

Security envelopes should be external to generated content.

# 22. Sandboxed iframe

For interactive AI-generated web apps:

```html
<iframe
sandbox="allow-scripts"
src="https://uuid.sandbox.example.net/">
</iframe>
```

Add sandbox capabilities individually.

Avoid casually adding both:

```text
allow-scripts
allow-same-origin
```

because that substantially changes the iframe security model.

For communication:

```text
postMessage()
```

with:

- exact origin checks
- schema validation
- typed message protocol
- capability-like request IDs

Never:

```js
if (event.data.command)
eval(event.data.command)
```

obviously.

Sanitizers are useful.

But I'd prefer:

```text

+
sanitize
```

```text

=
safe
```

- SVG
- MathML

- PDFs
- office documents

# 24. File ingress scanning / canonicalization

For AI-created artifacts or uploaded user inputs:

```text
input
↓
quarantine
↓
parser/canonicalizer
↓
scanner
↓
sandbox
```

Potential controls:

- archive recursion limit
- decompression ratio
- file count
- path traversal rejection

```text
↓
sandbox
```

# 26. Immutable source commits

Reference everything by hash:

```text
git SHA

package digest
toolchain digest
policy digest
```


# 27. TOCTOU protection

Policy decisions should bind to digests.

Bad:

```text
scan image:foo

```

Between those calls, `foo` can change.

Good:

```text

deploy sha256:abc
```

Same for:

- commits
- policies
- dependencies
- model-generated patches
- configuration

# 34. No persistent home directory by default

Persistent state is a hidden capability.

Prefer:

```text
new sandbox
fresh /home
fresh /tmp
fresh process tree
```

per task.

Explicitly import only the state required.

Otherwise malicious code can persist through:

- shell rc
- Git hooks
- compiler config
- package manager config
- SSH config
- credential helpers
- PATH modifications
- editor plugins
- build cache poisoning

# 35. Treat caches as hostile

Build caches are often overlooked.

A shared:

```text
ccache
sccache
pip cache
npm cache
cargo cache
Go cache
Docker layer cache
```

is effectively a communication/storage channel.

Safer:

```text
content-addressed immutable cache
```

or tenant-scoped writable cache.


instead of inherited process environment.


Especially:

```text
/var/run/docker.sock
/run/containerd/containerd.sock
```

# 38. Limit interpreters and compilers in production

Development/build sandboxes may need:

```text
gcc
python
shell
curl
```

Runtime images often don't.

Ship the narrowest runtime possible:

```text
static binary

```

rather than the full build environment.

# 39. No runtime package installation

Production workload doing:

```text
apt install ...
pip install ...
npm install ...
curl ... | sh
```

is a major design smell.

Build everything into an immutable artifact.

Runtime should be:

```text
artifact + configuration
```

not a second build system.

# 40. Policy-as-code with a trusted policy engine

Have a policy decision point outside AI control.

Conceptually:

```text
canDeploy(
artifact,
tenant,
provenance,
SBOM,
tests,
risk_class
)
```

Rules could be:

```text
deny if unsigned
deny if provenance missing
deny if builder untrusted
deny if dependency not approved
deny if critical vulnerability
deny if security-sensitive files changed without review
```

The agent can inspect policy failures, but not rewrite production policy.

# 41. Information-flow labels

For sophisticated systems, label data:

```text
PUBLIC
TENANT_SECRET
INTERNAL
CREDENTIAL
UNTRUSTED
```

Then enforce flows:

```text
TENANT_SECRET → arbitrary Internet DENY
CREDENTIAL → sandbox filesystem DENY
UNTRUSTED → deployment controller parse carefully
```

This starts looking like MAC / taint tracking / IFC rather than ordinary ACLs.

It's a powerful abstraction for agent systems because **prompt injection is fundamentally an unwanted information/control-flow problem**.

---

# 42. Separate instructions from data

AI-agent specific:

Never construct:

```text
system:
"Read this GitHub issue and obey it"
```

when GitHub issue content is untrusted.

Architecturally tag data:

```text
TRUSTED INSTRUCTION
UNTRUSTED CONTENT
TOOL RESULT
SECRET
```

And ideally make tool APIs enforce it rather than relying entirely on the LLM understanding textual delimiters.

For example:

```json
{
"task": "fix issue",
"issue_text": "...untrusted...",
"allowed_actions": [
"read_source",
"write_patch"
]
}
```

rather than allowing arbitrary shell/cloud operations.

---

# 43. Constrain agent tools

Give the agent:

```text
read_file(path)
write_file(path)
run_tests()
search_dependencies()
```

instead of:

```text
shell(command)
```

Capability-specific tools make authorization far easier.

A shell is approximately:

> `doAnything(string)`

which is a terrible security API.

If shell access is necessary, put **the shell itself inside the sandbox**.

---

# 44. Human approval where consequence is irreversible

You don't need humans for everything.

Require them for things like:

```text
production DB migration
IAM changes
deleting resources
publishing packages
changing DNS
changing signing keys
payment operations
security policy modifications
credential access
```

Make approval semantics precise:

> approve this digest/action,

not:

> approve whatever the agent does next.

Again, bind approval to immutable inputs.

# 45. Promotion rather than mutation

Prefer:

```text
dev artifact
↓
staging
↓
production
```

where **the same bytes** are promoted.

Avoid rebuilding separately for prod.

Otherwise you tested:

```text
artifact A
```

and deployed:

```text
artifact B
```

which weakens all of your preceding assurances.

---

# 46. Sandboxed migrations

Database migrations deserve their own execution class.

Instead of giving application startup:

```text
ALTER TABLE
DROP TABLE
```

use a migration runner with:

- separate identity
- controlled network path
- transactional execution where possible
- backup/checkpoint
- reviewed migration
- bounded DDL privileges

Don't make the application credential a DBA credential.

---

# 47. Separate read and write identities

Useful general pattern:

```text
source-reader
artifact-writer
dependency-reader
log-writer
```

not:

```text
ci-superuser
```

The compromise graph becomes much smaller.

---

# 48. Ephemeral infrastructure

For especially suspicious workloads:

```text
create VM
boot immutable image
inject task
execute
extract result
destroy VM
destroy disk
destroy network identity
destroy credentials
```

Persistent executor fleets accumulate strange state.

Ephemeral microVMs reduce persistence dramatically.

---

# 49. Confidential VMs / TEEs where appropriate

Different problem, but worth adding.

If you're worried not just about workload → host escape, but also:

> infrastructure operator / host → workload

then:

- AMD SEV-SNP
- Intel TDX
- confidential VMs

can protect guest memory and support attestation.

Kata currently documents support for confidential-computing environments such as TDX and SEV-SNP with remote attestation. citeturn812510search15

Not necessary for most AI-agent sandboxes, but relevant for sensitive multi-party workloads.

## The highest-value ideas beyond what you already listed

If I reduced everything above to the things I'd most strongly add to your list:

1. **Capability-based broker instead of passing credentials.**
2. **Trusted control plane physically/logically separated from AI/execution.**
3. **No direct Internet; authenticated per-workload egress proxy.**
4. **Data-diode-style input/output channels.**
5. **Immutable source snapshot into sandbox; patch/artifact out.**
6. **AI cannot modify policy, CI trust, hidden tests, or signing.**
7. **Secretless build environments.**
8. **Hermetic builds + SLSA provenance + artifact signing.**
9. **Hidden/reference tests outside agent access.**
10. **Content-address everything and bind approvals to digests.**
11. **Per-execution ephemeral state rather than long-lived agent machines.**
12. **Tenant-scoped caches—or preferably immutable content-addressed caches.**
13. **Separate registrable browser domain, not merely path/subdomain isolation.**
14. **Security headers injected by trusted proxy, not supplied by generated content.**
15. **Resource/DoS isolation as part of the threat model.**
16. **Information-flow classification: secret + Internet should rarely coexist.**
17. **Fine-grained tools instead of giving the agent an omnipotent shell.**
18. **Independent reviewer/verifier that doesn't share the generating agent's context.**
19. **Honeytokens/canary credentials for detection.**
20. **Promotion of identical verified bytes instead of rebuilding for production.**

The general principle I'd use to review the whole system is:

> **Assume any AI-writable byte becomes attacker-controlled. Then trace what authority those bytes can eventually influence.**

That's stricter—and much more useful—than asking whether the AI itself is "trusted."
