почему когда просишь ИИ сделать код/проект, так часто получается оверинжиниренное или bloated код?

---------------------

Потому что у LLM есть несколько системных причин писать код именно так. И да, это не просто «плохой промпт».

Главная проблема: **ИИ обычно оптимизируется не под минимальный код, а под код, который выглядит как максимально полноценное решение**.

Отсюда типичный результат:

```text
"сделай CLI, который читает JSON и выводит поле"
```

превращается в:

```text
src/
cli/
config/
domain/
services/
repositories/
adapters/
exceptions/
utils/
tests/
pyproject.toml
Dockerfile
README.md
```

плюс `AbstractJsonReaderFactory`.

Почему так происходит:

1. **Обучение сильно смещено в сторону “профессионально выглядящего” кода.**
В корпусе GitHub, блогов, Stack Overflow и документации полно enterprise-patterns, tutorial-кода и демонстраций архитектур. Простое:

```python
print(json.load(open(sys.argv[1]))["foo"])
```

выглядит менее «серьёзно», чем `JsonFileService`, хотя для задачи может быть объективно лучше.

2. **Модель боится недоделать больше, чем переделать.**
Если требования неполные, она часто имплицитно предполагает:
- вдруг потом понадобится расширять;
- вдруг будет несколько backend'ов;
- вдруг нужен dependency injection;
- вдруг нужно тестировать каждый слой;
- вдруг пользователь хотел production-ready.

И начинает проектировать под воображаемое будущее. Это классический speculative generality.

3. **LLM плохо чувствует стоимость абстракции.**
Человеческий инженер понимает, что каждый новый:
- interface,
- layer,
- config knob,
- generic,
- dependency,

имеет постоянную когнитивную стоимость.

Для модели дополнительные 80 строк — почти бесплатны. Она не будет полгода этот код поддерживать.

4. **Ей проще продолжать шаблон, чем остановиться.**
Autoregressive-модель буквально обучена продолжать последовательность. Появился:

```python
class UserRepository:
```

и дальше статистически естественно возникают interface, implementation, factory, DTO, mapper и tests.

Человек иногда думает: «Стоп. А зачем вообще repository?»
У модели такой тормоз слабее.

5. **“Best practices” легко превращаются в cargo cult.**
SOLID, DRY, clean architecture, dependency injection и прочее — не законы физики. Они полезны при определённых масштабах и проблемах.

LLM часто применяет их как универсальные добродетели:

> abstraction good → more abstraction better

Хотя нормальная инженерия часто скорее:

> duplication is cheaper than the wrong abstraction.

6. **Модель не знает реальную траекторию проекта.**
Хорошая архитектура появляется из знания:
- что реально меняется;
- что никогда не меняется;
- где реальные bottleneck'и;
- какие баги уже случались;
- кто поддерживает код.

LLM видит только prompt и поэтому архитектурно страхуется.

7. **Пользовательские слова сами провоцируют bloating.**
Особенно опасные:

- `production-ready`
- `scalable`
- `robust`
- `clean architecture`
- `enterprise-grade`
- `extensible`
- `best practices`

Для LLM это практически заклинание:

> please add 14 files.

8. **Большой ответ визуально кажется более полезным.**
Исторически модели поощрялись за полноту ответа. Поэтому есть латентная тенденция «показать работу»: добавить logging, validation, config, comments, types, retry logic, custom exceptions и ещё README на 150 строк.

Причём есть ещё забавная асимметрия: **LLM довольно хорошо умеет упростить существующий код, но хуже умеет сразу выбрать минимальную архитектуру.**

Поэтому гораздо эффективнее говорить ей не:

> Сделай хороший production-ready HTTP server.

а примерно:

> Реализуй минимальное решение.
> Используй стандартную библиотеку, если возможно.
> Не создавай абстракции, пока нет минимум двух реальных implementations.
> Не добавляй configurability, которую я не запросил.
> Не проектируй под гипотетические будущие требования.
> Предпочитай 1 файл вместо нескольких, если разделение не даёт явной пользы.
> Перед добавлением класса объясни, почему функции недостаточно.
> YAGNI > extensibility.
> Код должен быть boring.

Особенно сильная инструкция:

> **Implement only the requirements explicitly stated. Treat unspecified future requirements as nonexistent.**

Она заметно режет AI-slop.

И ещё лучше заставить модель делать архитектуру в два этапа:

> Сначала предложи самое простое решение, которое работает. Затем перечисли, при каких конкретных изменениях требований его действительно пришлось бы рефакторить.

Это переворачивает default с:

```text
"давайте заранее предусмотрим всё"
```

на:

```text
"сделаем просто, а абстракцию купим только когда она понадобится"
```

По сути, хороший AI-assisted coding сейчас требует от человека выполнять роль **редактора архитектуры**. LLM очень быстрый junior/mid, который знает чудовищное количество API и patterns, но которому нужно регулярно говорить:

> нет, `IUserFactoryProviderStrategy` нам нахрен не нужен.
